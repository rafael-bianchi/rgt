# RGT Spec Plan: Actionable Items from `weakpoints-and-growth-opportunities.md`

**Status:** Proposed — not yet executed
**Source:** `docs/weakpoints-and-growth-opportunities.md` §2 (distribution/CI), §3 (documentation accuracy), §5 (feature candidates). §4 (competitive landscape) is deliberately **not** turned into engineering specs here — see §3 of this document.
**Method:** Same as `docs/spec-plan-from-findings.md`/`docs/spec-plan-followups-from-verification.md` — each spec is an independently developable/testable/deliverable unit for an engineering agent's `/speckit-specify` + plan/tasks cycle. Only items the source report actually recommended *acting on now* got a spec number; items explicitly marked "don't build" or "no concrete trigger yet" are listed as declined/backlog instead (§2 below), so they aren't mistakenly picked up and implemented without a maintainer decision first.

## 2. Explicitly declined or deferred (not given spec numbers — do not implement without a fresh maintainer decision)

- **Local web dashboard for the provenance graph.** Research verdict: "don't build now" — no HTTP server crate exists in the dependency tree today, adding one works against the project's "single lightweight offline binary" positioning, and GitHub already renders Mermaid natively, covering most of the "I want to see it visually" demand `rgt graph -f mermaid` doesn't already satisfy.
- **Multi-project/workspace awareness.** Research verdict: "don't build" — the tool's actual use case is single-project; a monorepo already gets one shared graph for free by running `rgt init` at the root.
- **A third built-in verify operation** (beyond `EXPRESSION`/`DATE_DIFF`). Research verdict: "build later, on demand" — `EXPRESSION` already covers most custom-formula need; no concrete trigger exists yet. Revisit only if a real use case surfaces.
- **Docker image / `.msi`/winget/scoop packages.** Lowest-priority packaging gap identified; Windows CI/build/test already works, this is purely a discovery-convenience gap. winget was flagged as the lowest-effort option if Windows adoption specifically becomes a priority — not urgent enough for a spec number today.
- **`install.sh`'s own lack of self-verification** (curl-pipe-to-sh with no signature check on the script itself, though the downloaded binary archive *is* checksum-verified). Flagged as a known, common tradeoff many CLI tools accept — worth a maintainer risk-acceptance note (e.g. in `SECURITY.md`, see `032`'s similar treatment) rather than a code-change spec, unless the maintainer decides otherwise.

## 3. Not engineering specs at all — product/marketing actions for the maintainer directly

These came out of the same research pass (`docs/weakpoints-and-growth-opportunities.md` §4) but are **not appropriate to hand to a code-implementation agent** — flagging clearly so they aren't mistakenly attempted as `/speckit-specify` cycles:

- Launch on Hacker News/Reddit using real, citable 2025-2026 incidents (Deloitte's report refund, PwC's fabricated "thought leadership," KPMG's 5/45-accurate citations) as the pitch, with a short demo GIF.
- Pursue listing in `awesome-mcp-servers`/`awesome-claude-code` once there's real traction (do this *after* a launch, not instead of one — these lists gate on ~1,000+ stars).
- Publish a short comparison note positioning RGT against Guardrails AI/TruLens ("deterministic re-verification of a specific derived number" vs. "probabilistic groundedness scoring") to pre-empt an obvious objection.
- Consider concentrating demo/marketing polish on one flagship integration (Claude Code, given ecosystem size) rather than claiming uniform parity across all 13 agents.

## 4. Execution order

**P1 — user-facing correctness/discoverability, and the one big leverage play**
1. `040-fix-query-json-flag-behavior` — smallest, fully self-contained, do first to clear it off the board.
2. `034-crates-io-publish-rename` — independent, but needs a maintainer-approved name decision before `/speckit-specify` (see scope note).
3. `035-intel-mac-support-decision` — independent; needs a maintainer decision (build vs. reject) before `/speckit-specify`.
4. `036-release-versioning-reconciliation` — independent; do before the next release regardless of what else is in flight.
5. `038-translated-readme-resync` and `039-agent-instructions-feature-parity` — can run in parallel with each other and with 1-4; both are pure documentation-currency fixes with no code-behavior risk.
6. `041-mcp-server-mode` — its dedicated spec document (`docs/spec-041-mcp-server-mode.md`) now exists and is ready for `/speckit-specify`. It's the largest single item here and shouldn't block or be blocked by the smaller P1 items above; per its own Risks section, implement the zero-refactor `query_provenance` tool first as a de-risking prototype before touching the `execute_derive`/`run_verify_cli` refactor.

**P2 — hygiene, gated, or lower urgency**
7. `037-ci-pipeline-hygiene` — anytime, independent of everything else.
8. `042-status-check-github-action` — only after the open workflow-design question (scope note below) is resolved.

## 5. Scope notes

- **`034`**: the actual crate/package name is a maintainer decision this plan doesn't make unilaterally — candidates mentioned in the source research were `rgt-cli` or `rust-graph-tracker`; either way, the shipped **binary** name should stay `rgt` (via `[[bin]] name = "rgt"` in `Cargo.toml`, independent of the package/crate name), since that's the command every existing hook/install path already invokes. Document the collision explicitly in the README, mirroring how RTK's own README already handles its own "Rust Type Kit" naming collision.
- **`035`**: two valid resolutions exist — (a) add `x86_64-apple-darwin` to the `release.yml` build matrix and Homebrew formula, or (b) have `install.sh` explicitly detect Intel Mac and print a clear "not supported" message instead of a generic download failure, the same way it already handles other genuinely unsupported platforms. Pick one during `/speckit-specify`; don't half-implement both.
- **`036`**: going forward, the version number should only ever move via release-please's own automation — this spec's job is a one-time reconciliation (fix the manifest, backfill the changelog entries for specs `019`-`029`'s features, bump the Homebrew formula) plus confirming release-please's next run behaves correctly against the corrected state, not a process change beyond "stop hand-bumping."
- **`039`**: touches both static markdown (`AGENTS.md`, `CONTRIBUTING.md`) and Rust string constants (`src/hooks/glue/mod.rs`, `src/hooks/installer.rs::codex_section()`) — the latter requires a rebuild before the fix is actually live for any user who re-runs `rgt init`; consider whether existing users need a note that re-running `rgt init` (or `--force`) is required to pick up the corrected instructions text, given the idempotent-write behavior specs `019`/`028` already established.
- **`041`**: the standalone deep spec (`docs/spec-041-mcp-server-mode.md`) is written and ready — `/speckit-specify` can proceed directly from it. Its own Open Questions section (§7) flags three things to resolve during implementation, not before starting: exact `#[tool]` macro ergonomics (unvalidated against a compiling prototype), MCP-server cwd/project-root resolution assumptions, and whether `verify`/`derive` should stay two separate tools or collapse into one — none of these block starting the work, unlike `034`/`035`/`042`'s genuine pre-implementation blockers.
- **`042`**: **blocked on an open question the growth research flagged but didn't resolve**: this Action only provides real value if teams commit `.rgt/store.db` (a binary SQLite file) to their repo so CI can re-check it on every PR — and that's not an established, documented workflow anywhere in this project today. Resolve whether that's the intended usage pattern (and if so, document it) before specifying this Action; otherwise the spec will bake in an unconfirmed assumption about how the tool is meant to be used in CI.
