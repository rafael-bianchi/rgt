# Feature Specification: Numeric and Date Provenance Tracking

**Feature Branch**: `001-provenance-tracking`

**Created**: 2026-07-31

**Status**: Draft

**Input**: User description: "Numeric and date provenance tracking for LLM coding agents. RGT (Rust Graph Tracker) gives AI coding agents a persistent, queryable memory of every number and date they read from source files or derive through calculations, so they never silently reason from stale data."

## Clarifications

### Session 2026-07-31

- Q: Where and in what format should RGT persist its provenance graph state locally? → A: Embedded SQLite database in `.rgt/store.db` at project root using `rusqlite` with bundled SQLite, wrapped in transactions for cascading invalidation writes.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Automatic Downstream Staleness Flagging on File Edits (Priority: P1) 🎯 MVP

As a developer using an AI coding agent, when I edit a source file that backs a number or date the agent previously used in a calculation, I want every downstream value derived from that number to be automatically flagged as stale, so the agent never presents me with outdated results without warning me first.

**Why this priority**: Preventing silent reasoning errors from stale source data is the core problem RGT solves; without automatic invalidation cascades, agents will continue generating incorrect calculations based on modified files.

**Independent Test**: Can be tested by seeding a value from a test document, recording a derived calculation, modifying the source document timestamp/content, and asserting that the derived value query immediately reports a `stale` status.

**Acceptance Scenarios**:

1. **Given** a source file containing a recorded number `150` and a derived calculation `300` (`150 * 2`), **When** the source file is modified such that the source timestamp or content hash changes, **Then** querying the derived value `300` MUST immediately return `stale: true` along with the identity of the modified source file.
2. **Given** a chain of derived calculations A → B → C → D, **When** the source file backing A is updated, **Then** all downstream nodes (B, C, and D) MUST be flagged as stale without requiring a full rescan of un-impacted values.
3. **Given** a source file that is inspected but whose relevant content, size, and modification timestamp remain unchanged, **When** a staleness check is executed, **Then** all downstream values MUST remain `stale: false`.

---

### User Story 2 - Passive Capture of Source Numbers and Dates (Priority: P1)

As an agent, when I read a number or date from a source file during tool execution, the system should silently record that value and remember which file, line/location, and file snapshot (timestamp and hash) it came from.

**Why this priority**: Recording base values automatically without extra prompt overhead is required to establish the root nodes of the provenance graph.

**Independent Test**: Can be tested by invoking a tool read command on a source file, then querying the graph store to verify a root value node was created with accurate file metadata.

**Acceptance Scenarios**:

1. **Given** an agent reading a markdown, CSV, or configuration file, **When** the file reading tool action completes via passive execution hooks, **Then** extracted numeric values and ISO date strings are stored with source file path, line offset, file modification time (`mtime`), and file size.
2. **Given** repeated reads of an unchanged file, **When** passive hooks process the read event, **Then** existing value nodes are reused rather than creating duplicate graph entries.

---

### User Story 3 - Derived Calculation & Date Difference Provenance Recording (Priority: P1)

As an agent, when I combine two or more recorded values through an arithmetic calculation or date difference, the system should record a new derived node linked to its parent input nodes.

**Why this priority**: Derived values (e.g., date differences, totals, averages) represent the actual reasoning artifacts generated by agents that must be tracked for staleness.

**Independent Test**: Can be tested by recording two base values (e.g., `Start Date` and `End Date`), recording a date difference calculation (`Duration`), and verifying that a `Duration` node exists with directed edges from both date nodes.

**Acceptance Scenarios**:

1. **Given** two parent value nodes (e.g., `Date A` and `Date B`), **When** an agent performs a date-diff operation, **Then** a derived `Duration` node is added to the graph with directed edges connecting `Date A` and `Date B` to the new node.
2. **Given** multiple parent numeric nodes, **When** an arithmetic calculation (e.g., sum, product, ratio) is performed, **Then** a derived `Number` node is recorded storing the operator type, formula expression, and parent node references.

---

### User Story 4 - Derivation Chain Query ("Why is this value X?") (Priority: P2)

As an agent, I should be able to query the provenance system with "why is this value X" and receive a complete, structured chain showing the exact source files, raw values, and step-by-step calculations that produced value X.

**Why this priority**: Enables AI agents to explain their reasoning, audit complex data flows, and self-correct when reviewing code or design decisions.

**Independent Test**: Can be tested by querying a multi-level derived node ID and checking that the returned JSON payload contains an ordered tree/path of parent nodes leading back to root source file locations.

**Acceptance Scenarios**:

1. **Given** a derived value node in the system, **When** an agent queries the derivation provenance for that value ID via the query interface, **Then** the response includes the full ordered lineage tree including original file paths, line numbers, parent values, and mathematical operations.
2. **Given** a derived value where one of the upstream sources has become stale, **When** the derivation chain is queried, **Then** the response highlights exactly which step and source file caused the staleness.

---

### User Story 5 - Developer Staleness Inspection & Dependency Graph View (Priority: P2)

As a developer, I should be able to view a list of all currently stale values in the project, inspect why each value is stale, and render/view the dependency graph of values and their origin files.

**Why this priority**: Developers need visibility into agent memory health and project dependency state without having to reverse-engineer agent logs.

**Independent Test**: Can be tested by running the developer status CLI command in a repository with mixed valid and stale values, ensuring clean tabular output listing stale nodes and their invalidation sources.

**Acceptance Scenarios**:

1. **Given** a project repository with active provenance tracking, **When** a developer executes the status inspection command, **Then** a summary of total tracked nodes, active nodes, and stale nodes is displayed with human-readable file references.
2. **Given** a developer requesting a graph view, **When** the graph command is run, **Then** a structured representation (e.g., DOT/Mermaid format or terminal tree) of nodes and edges is produced.

---

### User Story 6 - One-Command Environment Auto-Configuration (Priority: P1)

As a developer, setting up provenance tracking for my coding agent should take a single command (`rgt init -g`), automatically detecting the active environment and configuring hooks for supported agent environments without manual configuration editing.

**Why this priority**: Frictionless developer experience is essential to ensure developers actually adopt and enable the tracking system across their preferred AI tools.

**Independent Test**: Can be tested by running `rgt init -g` in test environments representing Claude Code, Cursor, Codex CLI, and Windsurf, verifying that proper hook registrations are generated in each tool's configuration directory.

**Acceptance Scenarios**:

1. **Given** a developer environment with one or more supported AI coding tools installed (Claude Code, Cursor, Codex CLI, Windsurf), **When** `rgt init -g` is executed, **Then** global/project hooks for those tools are automatically detected and configured without user intervention.
2. **Given** an environment with no pre-existing tool configs, **When** `rgt init -g` runs, **Then** helpful output confirms which agent hooks were initialized and provides instructions for verification.

---

### Edge Cases

- **Deleted Source Files**: When a tracked source file is deleted from disk, all nodes anchored to that file MUST be immediately marked stale, with an explicit error tag (`FILE_DELETED`).
- **Concurrent File Writes**: When an agent or external build process writes to a file in rapid succession, two-tier detection MUST safely reconcile timestamps without corrupting graph state or blocking file access.
- **Circular Derivations**: If an agent attempts to record a calculation that would introduce a cycle in the dependency graph, the system MUST reject the edge and return an explicit cycle error.
- **Large File Hashing**: For source files exceeding 100MB, the system MUST rely exclusively on Tier 1 (`mtime` + size) checks unless forced by a full integrity verification request.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST maintain a persistent directed acyclic graph (DAG) of values, where root nodes represent values extracted from source files and intermediate/leaf nodes represent derived calculations.
- **FR-002**: System MUST support three first-class value data types: `Number`, `Date` (ISO-8601 timestamps), and `Duration` (temporal differences).
- **FR-003**: System MUST implement a two-tier file modification check (Tier 1: `mtime` + file size; Tier 2: BLAKE3 cryptographic content hash) to determine if a source file has changed.
- **FR-004**: System MUST perform "no-change" status evaluation in under 1 millisecond (1ms) per file.
- **FR-005**: System MUST automatically cascade staleness flags to all downstream dependent nodes whenever an upstream source file changes, touching strictly the affected reverse-dependency subgraph.
- **FR-006**: System MUST provide passive background event capture hooks (`PreToolUse` and `PostToolUse`) compatible with supported AI agent execution loops.
- **FR-007**: System MUST provide a Model Context Protocol (MCP) server interface enabling AI agents to actively record values, record derivations, and query derivation chains.
- **FR-008**: System MUST support date difference (`date-diff`) calculations as first-class derived values producing `Duration` nodes linked to parent `Date` nodes.
- **FR-009**: System MUST provide a `rgt init -g` command that auto-detects and configures hooks for Claude Code, Cursor, Codex CLI, and Windsurf without manual configuration file edits.
- **FR-010**: System MUST expose a derivation query interface ("Why is this value X?") returning the complete, ordered provenance lineage of any recorded node.
- **FR-011**: System MUST provide CLI developer commands to list all stale values, inspect node details, and output graph structure.
- **FR-012**: System MUST operate cross-platform on macOS (x86_64, aarch64), Linux (x86_64, aarch64), and Windows (x86_64) as a single standalone executable with zero external runtime dependencies.
- **FR-013**: System MUST handle file system operations safely without blocking host agent execution loops if passive hook recording encounters an unexpected write error.
- **FR-014**: System MUST assign every recorded node a unique, deterministic ID based on its origin or derivation parameters.
- **FR-015**: System MUST prevent duplicate root node creation when identical values at the same file location and version are re-read.
- **FR-016**: System MUST persist all graph nodes, derivation edges, and source file metadata in an embedded SQLite database located at `.rgt/store.db` within the project root directory, utilizing bundled SQLite (`rusqlite`) wrapped in transactions for write safety during invalidation cascades.

### Key Entities

- **Source Document**: A physical file on disk (markdown, CSV, code, configuration) identified by absolute path, modification timestamp (`mtime`), file size, and BLAKE3 hash.
- **Tracked Value**: A discrete node in the provenance graph representing either a raw value (`Number`, `Date`) read from a source file location or a derived value (`Number`, `Date`, `Duration`) resulting from a calculation.
- **Derivation Edge**: A directed connection from parent value node(s) to a child derived value node, annotated with the operation type (arithmetic operator, date diff, transform).
- **Provenance Graph**: The overall directed graph mapping relationships between source files, raw values, derivation edges, and downstream values, persisted in `.rgt/store.db` (SQLite) and managing staleness invalidation state via transactional updates.
- **Agent Integration Surface**: The combination of passive tool execution hooks (`PreToolUse`/`PostToolUse`) and active query mechanisms (MCP server stdio RPC) through which AI agents communicate with the graph.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 100% of values derived from a modified source file are automatically marked as `stale` upon source file edit, with zero manual re-checks required.
- **SC-002**: "No-change" file staleness evaluation completes in under 1 millisecond (1ms) per file.
- **SC-003**: Derivation query ("Why is this value X?") returns complete provenance chains back to root source files for 100% of valid graph nodes.
- **SC-004**: One-command initialization (`rgt init -g`) successfully sets up agent hooks in under 5 seconds with zero manual configuration file edits.
- **SC-005**: Passive hook operations complete in under 5 milliseconds, ensuring normal AI agent tool execution is completely unhindered by background recording.

## Assumptions

- AI coding agents execute file read and calculation operations using standard tool calls that can be intercepted via standard hook protocols or queried via MCP tools.
- Source files tracked by RGT reside on local file systems accessible to the RGT binary.
- Standard ISO-8601 string representations are used for date values passed by agents.
