# Feature Specification: Export Provenance as Turtle

**Feature Branch**: `develop` (specification only; no feature branch created)

**Created**: 2026-09-24

**Status**: Draft

**Input**: User description: "Node IDs are content-addressed, so Turtle graphs from separate projects could merge on shared identity. The hook layer knows which of the 13 agents fired an event, but that identity is not stored. Export the provenance graph in Turtle, represent agents, and keep the exporter small."

## Clarifications

### Session 2026-09-24

- Q: When two separate projects export values with the same RGT node ID, should a graph reader treat them as one value or keep them separate? → A: Keep independent projects distinct; shared identity is outside this feature.
- Q: When someone exports a project's provenance for sharing, should absolute source file paths appear by default? → A: Use project-relative paths by default; include absolute paths only on request.
- Q: If RGT knows a result's parent values but cannot prove how they formed one calculation, should the Turtle export keep the supported links or fail? → A: Export supported links; omit and report the uncertain activity.
- Q: When the same coding agent captures the same value more than once, should the export show every capture or only that the agent captured it? → A: Show one association per agent and value; collapse repeat captures.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Share a project's lineage (Priority: P1)

A developer exports a project's recorded numbers and dates in Turtle, a standard graph format. A separate provenance reader can identify each value, its source, and its recorded derivations without translating RGT's existing visual graph formats.

**Why this priority**: A usable, truthful export is the smallest independently valuable part of the proposal.

**Independent Test**: Record a source value and a result derived from two parents, export the graph, and inspect it with an independent Turtle reader. Confirm the values, source locations, parent relationships, and derivation direction match RGT's recorded graph.

**Acceptance Scenarios**:

1. **Given** a project with a root value from a file inside that project, **when** the developer requests Turtle from the graph export command, **then** the output is valid Turtle and identifies the value, its type, project-relative source path, source line when known, and stale state.
2. **Given** a recorded result with two parents and one unambiguous derivation, **when** the developer exports the graph, **then** the result is represented as an entity generated by an activity that used both parent entities, with the recorded operation and expression when available.
3. **Given** a stored lineage that does not establish a unique derivation activity, **when** the developer exports it, **then** the export succeeds with supported parent-child lineage, omits the uncertain activity and its operation/expression claim, and reports the omission outside the Turtle content.
4. **Given** an unchanged project, **when** its Turtle export is repeated, **then** the same facts appear in the same order; the existing graph formats and recorded verification state remain unchanged.
5. **Given** an empty project or recorded text requiring escaping, **when** the developer exports it, **then** an independent reader accepts the result and recovers the original text where present.
6. **Given** an export error, **when** the developer requests Turtle, **then** they receive an actionable error and no partial graph is presented as complete.
7. **Given** a source outside the project, **when** the developer exports without requesting full paths, **then** its source has a path-free identifier; when they explicitly request absolute paths, the available absolute source path appears.
8. **Given** a project beyond the documented Turtle export limits, **when** the developer requests Turtle, **then** the command reports the exceeded limit and exits without presenting a partial graph as complete.

---

### User Story 2 - Combine project exports safely (Priority: P2)

A developer combines two exported graphs using an ordinary standards-compatible graph reader. The result keeps values from independent projects distinct, even if both projects recorded the same value at the same relative file path and line. Repeated exports from one project still refer to the same recorded nodes.

**Why this priority**: Existing node IDs are deterministic for their inputs, but those inputs do not prove global identity across projects. Safe graph combination requires a clear identity rule.

**Independent Test**: Create two independently initialized projects with matching relative paths, lines, and values; export each twice; combine the outputs with an independent graph reader. Compare identities within and across projects.

**Acceptance Scenarios**:

1. **Given** two exports of the same unchanged project, **when** they are compared, **then** each recorded node has the same graph identity in both exports.
2. **Given** independently initialized projects with matching local node IDs, **when** their exports are combined, **then** the values remain distinct and retain their respective project and source context.
3. **Given** two project exports, **when** a standards-compatible reader combines them, **then** no RGT-specific merge operation is required.

---

### User Story 3 - See which agent captured a value (Priority: P3)

A developer can see which supported coding agents captured a value. If both Cursor and Claude Code capture the same value, the export shows both agents; repeat captures by either agent do not create an event history. It does not claim that either agent authored the source value merely because it read or recorded it.

**Why this priority**: The agent name is available during hook execution but is not currently retained with recorded values. Reliable attribution needs durable evidence before it can appear in an export.

**Independent Test**: Capture one value twice through one supported agent hook and once through another, then export later in a separate process. Confirm exactly one association per agent and value. Compare with a manually recorded value and a historical value with no stored agent evidence.

**Acceptance Scenarios**:

1. **Given** a value captured through a recognized agent hook, **when** the project is exported later, **then** the graph identifies that agent as associated with the value's capture activity.
2. **Given** the same value captured by two agents, **when** the graph is exported, **then** one capture association for each agent remains visible.
3. **Given** a historical or manual record without agent evidence, **when** it is exported, **then** no agent or authorship attribution is fabricated.
4. **Given** an unrecognized agent or a failed passive capture, **when** the host tool continues and a graph is later exported, **then** the host was not blocked and the export contains no unsupported attribution for that event.
5. **Given** the same agent captures the same value repeatedly, **when** the graph is exported, **then** it contains exactly one association between that agent and value.
6. **Given** an integration that supplies instructions but no hook event, **when** its user records a value manually, **then** the export does not infer that integration's agent identity.

### Edge Cases

- An empty project exports a valid, empty graph.
- Project-relative source paths, disclosed absolute paths, expressions, and values containing quotes, backslashes, line breaks, or non-ASCII text remain valid and intact in the export.
- A source outside the project is identified without revealing its absolute path by default, including through its graph identifier.
- Historical shorter node IDs remain referable; export does not rewrite recorded identity.
- If several stored edges point to one result but cannot be grouped into a unique derivation, the export retains only relationships supported by the stored evidence and reports the ambiguity outside the Turtle content.
- A hook event without a recognized agent, or a failed capture, adds no false agent attribution and does not block the host coding tool.
- Re-recording a value through a different agent does not erase an earlier supported capture attribution.
- Repeated captures of one value by the same agent do not create duplicate associations.
- A project beyond the supported Turtle size limits receives an actionable export error; its stored graph and the existing graph formats remain usable.
- A store lock or output sink that consumes the command's one-second budget results in a nonzero exit. A failed write may leave incomplete bytes in the sink, but is never reported as a complete export.

## Requirements *(mandatory)*

### Functional Requirements

Successful-export requirements below apply to a selected project within FR-014's Turtle limits whose output completes before the command-wide deadline. FR-014 defines the error behavior outside that supported domain.

- **FR-001**: Users MUST be able to request Turtle from the existing project graph export command using `--format ttl`, and the result MUST be readable by an independent Turtle reader.
- **FR-002**: For a selected project within the documented Turtle export limits, a successful export MUST include every recorded root and derived value, preserving its recorded value type, value, and stale state. A project beyond any limit MUST receive an actionable error with no Turtle written.
- **FR-003**: Each recorded value MUST be represented as a `prov:Entity`. For each unambiguous recorded derivation, a `prov:Activity` MUST `prov:used` every recorded parent, the child MUST `prov:wasGeneratedBy` that activity, and the child MUST `prov:wasDerivedFrom` its parents.
- **FR-004**: Root values MUST retain their source identity and available line information. In the default export, sources inside the project MUST use project-relative paths, sources outside it MUST use path-free identifiers, and project and source identifiers and source-location fields MUST NOT disclose absolute local paths. Users MUST be able to explicitly request available absolute source paths. A supported derivation activity MUST retain its recorded operation and expression when available. When no unique activity is supported, stored edge labels MUST NOT be presented as one verified operation or expression.
- **FR-005**: When the stored evidence cannot uniquely identify a derivation activity, the export MUST succeed with only supported direct lineage, omit the uncertain activity, and report the omission outside the Turtle output.
- **FR-006**: Graph identities for recorded nodes MUST be stable across repeated exports of the same project, including nodes with historical ID lengths.
- **FR-007**: Graph identities from independently initialized projects MUST remain distinct when local node IDs happen to match. The original RGT node ID MUST remain available in the export for comparison.
- **FR-008**: Users MUST be able to combine project exports in a standards-compatible reader without an RGT-specific merge command. Matching local node IDs alone MUST NOT assert that two projects' values are the same entity. Declaring shared identity across projects is outside this feature.
- **FR-009**: For future hook captures where one of the supported agent identities is known, the system MUST retain that identity with the capture evidence so later exports can identify the responsible agent.
- **FR-010**: The system MUST retain one durable capture association per known agent and recorded value. Repeated captures by the same agent MUST NOT create duplicate associations; captures by another agent MUST add a distinct association without overwriting existing ones.
- **FR-011**: Each capture association MUST appear as one capture `prov:Activity` that `prov:used` the recorded value and `prov:wasAssociatedWith` the known coding `prov:Agent`. The export MUST NOT assert source authorship or derivation responsibility without separate evidence. Historical and manual values without agent evidence MUST have no invented agent association.
- **FR-012**: Turtle export and agent capture MUST preserve the current behavior of value extraction, derivation verification, staleness tracking, and existing graph formats.
- **FR-013**: Repeated exports of an unchanged project MUST present the same graph facts in a consistent order. Empty graphs and text requiring escaping MUST still produce valid Turtle.
- **FR-014**: Turtle export MUST enforce a one-second command-wide deadline, including store access and output writing, and MUST reject a project above 10,000 recorded values, 30,000 derivation edges, or 64 MiB of rendered UTF-8 Turtle. Exceeding a size limit, store failure, or pre-output deadline MUST produce an actionable error with zero stdout bytes. A deadline or OS failure during the final write MUST return nonzero and MUST NOT present partial bytes as a complete graph, including when stdout is a non-reading pipe. Passive hook failures MUST continue to leave the host agent unblocked.

### Key Entities *(include if feature involves data)*

- **Recorded value**: A number, date, or duration with a local node ID, value type, value, stale state, and optional source location.
- **Source document**: The recorded file context from which a root value was extracted, identified by a project-relative path or a path-free identifier in the default export.
- **Derivation**: Recorded evidence that one or more parent values contributed to a child value, with an operation and optional expression.
- **Project identity**: The context that distinguishes independently initialized projects while keeping one project's exported node identities stable.
- **Capture association**: Durable evidence that a supported agent hook captured a recorded value at least once, represented once per agent and value; it can be absent for historical or manual records.
- **Agent**: The normalized identity of the coding tool associated with a capture, distinct from the author of a source value.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: In representative fixtures covering roots, dates, durations, single-parent and multi-parent derivations, 100% of exported graphs parse in an independent Turtle reader and expose every recorded value and supported lineage relationship.
- **SC-002**: In a two-project fixture with matching local node IDs, combined exports retain two distinct value identities; in two unchanged exports of either project, 100% of that project's node identities remain stable.
- **SC-003**: In fixtures covering every event-capable agent integration, 100% of successful future hook captures with a known agent show the correct association after a fresh export, with exactly one association per agent and value even after repeated captures.
- **SC-004**: In historical, manual, unknown-agent, and ambiguous-derivation fixtures, the export makes zero unsupported claims about agents, authorship, or unique derivation activities.
- **SC-005**: A developer or downstream reader can answer the value, source reference, parents, and known capturing agents for every applicable fixture from the combined graph alone, without consulting RGT's visual graph formats.
- **SC-006**: On a standard, GitHub-hosted x86_64 `ubuntu-24.04` runner, the fixed 10,000-value fixture defined in the [export contract](contracts/turtle-export-contract.md), containing 6,000 roots, 4,000 derived values, 6,000 referenced sources, 8,000 edges, and 10,000 agent-value associations, completes process startup, snapshot, rendering, and local-file output in under 1 second in every measured release-build run. Fixtures at each remaining value, edge, and byte limit also complete in under 1 second; fixtures one unit over each limit return an actionable error within 1 second. A non-reading stdout pipe causes a nonzero timeout exit within the command-wide deadline on Linux, macOS, and Windows. Existing graph views keep their results.
- **SC-007**: Across fixtures with sources inside and outside the project, default exports expose zero absolute project or source-document paths through project and source identifiers and source-location fields; explicit full-path exports show 100% of available absolute source paths.

## Assumptions

- This specification records a proposed interoperability capability. The existing assessment found no named downstream consumer or observed exchange task, so implementation priority still needs a separate go/no-go decision.
- The first export covers the currently selected project's recorded graph. Automatic discovery of other projects and an RGT-specific merge tool are outside scope.
- Turtle export is intentionally bounded: 10,000 recorded values, 30,000 derivation edges, and 64 MiB of rendered UTF-8 Turtle. Each root references at most one source, so referenced source count is already bounded by value count. The eight eligible agents and one association per agent and value similarly bound capture associations without another quota. Larger projects require a separately specified exchange mechanism; Turtle limits do not restrict recording, querying, or existing graph formats.
- Project-scoped graph identity is the safe default. A matching content-derived local ID is useful comparison evidence, but it does not prove that values from separate projects share real-world identity.
- A source outside the project remains identifiable through a path-free source reference in default exports; full local paths require an explicit export choice.
- Path privacy applies to RGT-generated identifiers and source-location fields. User-supplied free text such as a recorded expression is preserved verbatim and may itself contain a path-like string.
- Future agent attribution requires durable capture evidence. A serializer alone cannot reconstruct the agent for existing records, and this specification does not prescribe how the evidence is stored.
- Agent attribution is a summary of which agents captured each value, not a history of every hook event.
- RGT configures 13 agent integrations, but only eight currently provide programmatic hook or plugin capture events. The five instructions-only integrations cannot supply agent attribution without a separate capture feature.
- A hook's agent identity establishes who triggered a capture event, not who authored the source file or created the numeric or date value.
- Turtle and PROV-O are the external exchange contract. The implementation plan will choose the smallest approach consistent with correctness, portability, and the project's dependency policy.
